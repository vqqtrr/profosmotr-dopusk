# Ответ на запрос 1. Предлагаемая структура решения

Задачу понял так: сервис сам берёт выгрузки 1С и qMS, связывает студентов с пациентами, по справочнику правил считает статус 14 обследований и итог допуска, а методист видит результат по своей группе с объяснением. Ниже структура. Код напишу после того, как ты её посмотришь.

## 1. Общая схема

```
 data/source/*.csv        rules/*.csv
 (выгрузки 1С и qMS)      (справочник правил)
        │                        │
        ▼                        ▼
 ┌──────────────┐        ┌───────────────┐
 │ 1. Загрузка  │        │ 3. Правила    │
 │   loader     │        │   rules       │
 └──────┬───────┘        └───────┬───────┘
        ▼                        │
 ┌──────────────┐                │
 │ 2. Сопостав- │                │
 │   ление      │                │
 │   matching   │                │
 └──────┬───────┘                │
        ▼                        ▼
 ┌──────────────────────────────────────┐
 │ 4. Расчёт статусов и итога  (calc)   │
 │    результат пишется в витрину       │
 └──────────────────┬───────────────────┘
                    ▼
            База SQLite (один файл)
                    ▼
 ┌──────────────────────────────────────┐
 │ 5. Сервер (api): отдаёт данные       │
 └──────────────────┬───────────────────┘
                    ▼
 ┌──────────────────────────────────────┐
 │ 6. Экран методиста (браузер)         │
 └──────────────────────────────────────┘
```

Главная идея: **всё считается один раз при загрузке данных** и складывается в готовую витрину. Экран только читает из неё, поэтому группа открывается мгновенно (NFR-01, до 5 секунд). В реальной системе это соответствовало бы ночному обновлению: загрузили, пересчитали, утром всё готово.

## 2. Части сервиса

| № | Часть | Что делает | Требования |
|---|---|---|---|
| 1 | **Загрузка** (`loader.py`) | Читает CSV из `data/source` и кладёт в базу «как есть», в таблицы с префиксом `src_`, повторяющие физическую модель. Каждая загрузка полностью заменяет старые данные одной транзакцией: дублей быть не может, а при ошибке остаются прежние данные. Запоминает дату среза из `export_meta.json`. | п. 1 |
| 2 | **Сопоставление** (`matching.py`) | Приводит ФИО к одному виду (нижний регистр, один пробел, ё → е), из СНИЛС оставляет цифры. Ищет пациента по трём полям. Если совпали два из трёх, связи нет, но запись помечается как «частичное совпадение» с указанием, какое поле не совпало. | FR-03, п. 2 |
| 3 | **Правила** (`rules.py` + папка `rules/`) | Загружает справочник правил из CSV-файлов. В коде нет ни одного кода услуги и ни одного срока. | п. «Правила отдельно» |
| 4 | **Расчёт** (`calc.py`) | Для каждого студента собирает все записи qMS по всем его эпизодам, для каждого из 14 обследований берёт последнее событие и определяет статус. Потом считает итог и формулирует причину. Для каждой ячейки запоминает, на основании какой записи qMS она поставлена. | FR-05, FR-06, БП-1, БП-2 |
| 5 | **Сервер** (`api.py`) | Небольшой веб-сервер: отдаёт списки для фильтров, таблицу группы, детали ячейки, список несопоставленных. | UC-01 |
| 6 | **Экран** (`static/`) | Одна страница: фильтры, сводка, таблица с цветами, всплывающая карточка по клику на ячейку. | US-1, п. 5 |
| 7 | **Тесты** (`tests/`) | Автотесты по 12 тест-кейсам плюс отдельные проверки «узких мест»: нормализация ФИО, граница 30 дней, последний результат. | Приёмка |

## 3. Таблицы в базе

**Исходные (как в выгрузках):** `src_one_c_imo`, `src_patient`, `src_episode`, `src_usluga186`, `src_usluga293`, `src_usluga294`, `src_analyz`, `src_ref_usluga`, `src_ref_analyz`.

**Справочник правил** (загружается из `rules/`):

| Таблица | Что хранит |
|---|---|
| `rule_exam` | 14 обязательных обследований: раздел, короткое название, код услуги qMS, вид проверки (осмотр / анализ / прививка / ФЛГ), срок действия в месяцах (пусто, если срока нет), порядок колонки на экране |
| `rule_bad_conclusion` | Фразы в заключении, при которых обследование не в норме: «направлен на дообследование» (терапевт), «направлен к фтизиатру» (ФЛГ) |
| `rule_ok_result` | Ответы анализов, которые считаются нормой: «отрицательно», «не обнаружены» |
| `rule_setting` | Общие настройки: порог «скоро закончится» = 30 дней |

**Результат расчёта (витрина):**

| Таблица | Что хранит |
|---|---|
| `student` | Студенты из 1С: ФИО, уровень, факультет, курс, группа |
| `student_match` | Связь студента с пациентом qMS: тип совпадения (полное / частичное / не найден), что не совпало |
| `exam_status` | Одна строка = студент × обследование: статус, текст для ячейки («20 дн. осталось»), цвет, ссылка на запись qMS, дата и текст источника (заключение или результат) |
| `admission` | Одна строка на студента: итог, причина, дата расчёта |

## 4. Как устроен справочник правил

Правила лежат в обычных CSV-файлах в папке `rules/`. Аналитик открывает их в Excel, меняет и перезапускает загрузку. Программист не нужен. Пример `rules/exams.csv`:

```
раздел;название;код_услуги;вид;срок_мес;порядок
Контроль на входе;ФЛГ;A06.09.006;ФЛГ;12;1
Контроль на входе;АДСМ;ВАК.АДСМ;прививка;120;2
Анализы;RW;A26.06.082;анализ;;9
Специалисты;Терапевт;B01.047.001;осмотр;;10
...
```

Если, например, решат, что офтальмолог тоже обязателен, достаточно добавить строку: на экране появится 15-я колонка, и итог начнёт её учитывать.

## 5. Логика статуса одного обследования

1. Найти все услуги с нужным кодом за все эпизоды пациента. Отменённые не учитываются.
2. Если таких нет: **«Нет данных»**.
3. Взять самую позднюю. Для прививок «поздняя» считается по дате вакцинации из сертификата, для остального по дате события в qMS.
4. Дальше по виду:
    - **анализ:** результата нет → «Ждёт результата»; ответ из списка нормальных → «Норма», иначе «Не в норме»;
    - **осмотр или ФЛГ:** не выполнено → «Назначено, не выполнено»; заключение содержит «плохую» фразу → «Не в норме»;
    - **если есть срок действия:** считаем дату окончания; прошла → «Просрочено n дн.», осталось ≤ 30 дней → «Скоро закончится, n дн.», иначе «Норма».
5. Итог «Допуск», если все 14 в «Норме» или «Скоро закончится». Причина собирается из всех остальных статусов по порядку колонок.

## 6. Технологии

- **Python 3** и встроенная в него **SQLite**: база в одном файле, ничего ставить не нужно.
- **FastAPI** для сервера. Он простой и бонусом сам делает страницу `/docs` со списком всех запросов сервера: на защите удобно показать, что экран получает данные через API.
- **Обычные HTML, CSS и JavaScript** без сборщиков: страница открывается сразу, а код легко прочитать.
- **pytest** для автотестов.
- Запуск одной командой `./run.sh`: создаёт окружение, ставит 3 библиотеки, загружает данные, считает и открывает браузер.

## 7. Структура папок

```

│   ├── loader.py          1. загрузка
│   ├── matching.py        2. сопоставление

│   ├── calc.py            4. расчёт статусов и итога
│   ├── api.py             5. сервер

└── docs/                  описание данных и история запросов
```

## 8. Вопросы к тебе перед реализацией

1. **Цвета.** Предлагаю серым показывать всё, где данных пока нет или они не готовы: «Нет данных», «Назначено, не выполнено», «Ждёт результата». Красным только реальную проблему: «Просрочено», «Не в норме», плохой ответ анализа. Итог в обоих случаях «Недопуск». Так методист сразу отличает «надо подождать» от «надо разбираться». Согласен?
2. **Причина.** Перечислять все проблемы или первые три и «ещё n»? Предлагаю все: обычно их одна-две.
3. **Частичные совпадения.** В таблице группы показывать как «Нет данных qMS (частичное совпадение: СНИЛС)», а под таблицей отдельным блоком список несопоставленных студентов группы с причиной. Подходит?
4. **Пациенты вне контингента** (есть в qMS, нет в 1С) на экран методиста не выводятся: это не его студенты. Согласен?
